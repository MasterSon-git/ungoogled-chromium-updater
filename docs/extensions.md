# Extension maintenance

The launcher reads extension registrations across the configured user-data directory. It discovers new extensions, includes disabled entries, and checks only approved sources. Built-in entries are serviced with Chromium. After a browser install the launcher refreshes the inventory immediately and reconciles it again on the first check following a standard launcher handoff. Profiles that have yet to start are picked up on later checks. Use `Update.ps1 -CheckOnly -VerifyCurrent` to inspect the latest registrations on demand.

## Install a verified update

1. If the updater reports that Chromium needs a setting change, open `chrome://flags/#extension-mime-request-handling`, select **Always prompt for install**, and relaunch Chromium. The updater keeps the verified update pending and retries the next time you open it normally, even if the regular check is still hours away. [Ungoogled Chromium extension FAQ](https://github.com/ungoogled-software/ungoogled-chromium-wiki/blob/master/faq.md)
2. On a due regular launcher run, the updater opens Chromium with your original arguments and working directory. It then passes the verified local CRX paths to the running browser in a separate invocation for each affected profile. Multiple updates in one profile can produce overlapping Chromium prompts. Review each extension, any changed permission or scope fields printed by the updater, and the requested permissions in Chromium. Keep disabled extensions disabled.
3. A handoff is a request. The next check verifies the actual installed ID, version, source and audited manifest fields when the signed package is available. If Chromium delayed activation, restart it and open the updater again. A declined, closed or otherwise incomplete prompt leaves the previous version pending. To retry, hold **Shift** while opening **Chromium Updater**, then type **R** and press **Enter** in its console. Press **Enter** by itself to continue normally.

Automatic handoff requires a regular launch of the configured browser and user-data directory and a responsive Chromium window in that directory. Private, app, headless and alternate user-data launches keep their original behavior. If the request fails before Chromium starts it, the console reports the failure and retains the exact staged CRX.

For manual installation, use the console's staged CRX path and open it as a local file URL in the named profile. If needed, use signed drag-and-drop on `chrome://extensions` as documented by upstream. The filename includes the expected SHA-256. For advanced maintenance, `Update.ps1 -Stage` saves packages without launching Chromium, `-CheckOnly -VerifyCurrent` checks installed versions, and `-RetryExtensionUpdates` requests pending prompts again.

The cache is private and capped at 256 MiB. Staging prunes managed cache files older than seven days when it needs to write a candidate. If the cache is full, remove unneeded CRXs from `extension-packages` while the updater is idle. Rerun staging to obtain a fresh verified copy if a package is missing. Use one installation workflow per candidate. Leave Chromium Web Store installed and available for its Store workflow.

The permission review compares required and optional permissions separately. Each static content-script rule retains its script and CSS lists, matches, include and exclude filters, frame behavior, execution world and timing. Changes such as moving a script to another rule or dropping a filter are flagged. Selected manifest restrictions, including CSP and external connections, are compared for additions, changes and removals. This conservative comparison may flag narrowing or other edits for review. Dynamic registrations, extension code, actual grants and Chromium's permission warning calculations are outside this comparison.

## Chrome Web Store

For an approved ID, the coordinator queries Google's Chrome Web Store update endpoint with the extension ID and browser version. This endpoint can return version, package location, SHA-256 and length. The updater validates the extension's developer proof and Chromium's pinned production Web Store publisher proof before presenting a new package for review. Availability may vary with browser version and staged rollout.

Chromium Web Store by NeverDecaf supports installation from the Store and user-initiated update prompts. Its automatic checks populate the badge. Clicking an individual update starts a fresh download, so the version offered there can differ from the package staged for the launcher. The launcher uses the same native handoff for verified Store packages and the helper's own stable GitHub CRX. A userscript manager's own script updates are separate. [Chromium Web Store usage](https://github.com/NeverDecaf/chromium-web-store/tree/v1.5.5.4)

The Windows fork's extension downloader patch disables the native manifest fetch queue. A Store or off-store update URL and the **Update** button in `chrome://extensions` therefore do not provide unattended installation. The helper has no supported interface for the launcher to hand it an exact verified CRX. Its permission and channel configuration remain user-managed. Enterprise force-install can implicitly grant permissions and prevent users from disabling extensions, so it is unsuitable for these per-user updates. [Ungoogled Chromium updater patch](https://github.com/ungoogled-software/ungoogled-chromium/blob/f45ef24307dce0fb5a53e4db4d7e35cdf159745f/patches/core/ungoogled-chromium/disable-webstore-urls.patch) [Chromium force-install policy](https://chromium.googlesource.com/chromium/src/+/HEAD/components/policy/resources/templates/policy_definitions/Extensions/ExtensionInstallForcelist.yaml)

The helper uses extension management, downloads, storage, alarms, context menus, and host access on supported stores. Its update checks can query channels beyond the launcher's approved list. Review its permissions before enabling additional sources. [Published helper source](https://github.com/NeverDecaf/chromium-web-store/tree/v1.5.5.4/src)

## Full uBlock Origin

The original Chrome Web Store ID is `cjpalhdlnbpafiamejdnhcphjbkeiagm`. Raymond Hill publishes the current full Chromium extension as a signed CRX on GitHub with ID `fkgkibajhfbepljeaefdnfnegdcjomkh`. Its official update manifest maps the new ID to the release artifact. In-place updates of the GitHub ID use the exact verified CRX. The original Store ID requires the manual migration below. The browser compatibility gate tests the latest verified stable full uBlock Origin on the candidate Windows payload. Each profile's installed version and update status are reported independently. A pending or failed extension update leaves that installed combination unverified. [Signed releases](https://github.com/gorhill/uBlock/releases/latest) [Official update manifest](https://github.com/gorhill/uBlock/blob/master/dist/chromium/update.xml)

For an ID migration:

1. Open the legacy extension's dashboard, go to Settings, then choose **Back up to file**. Save it in the private updater directory. Save My filters, My rules, and Trusted sites separately if you use those features. Note the extension's enabled state, custom browser site access, and any file or incognito access you intentionally granted. Review the [publisher's backup instructions](https://github.com/gorhill/uBlock/wiki/Dashboard%3A-Settings).
2. Back up the closed profile and validate the intended Windows browser build before migration. Choose the signed Chromium `.crx` from the official stable GitHub release. Use the supported Chromium prompt. The signed replacement has a new identity and Chromium requires explicit confirmation. If no prompt appears, check the upstream-supported CRX installation flow. Keep the old extension and use the backup if the signed installation cannot be completed.
3. Restore the JSON in the new extension's dashboard. Verify filters, dynamic rules, trusted sites, imported lists, and selected settings. Restore browser-side grants deliberately if needed. Temporarily disable the legacy extension during the comparison, keep its backup, and reproduce the old enabled state after testing.
4. Test the new extension with the [uBlock Origin logger](https://github.com/gorhill/uBlock/wiki/The-logger) and a safe request you expect to be blocked. Verify the same request succeeds with filtering paused for that test site, then restore filtering. Confirm the new ID and exact installed version in `chrome://extensions`, and run the launcher's signed channel check. The next signed update can be verified the same way.
5. Remove the legacy extension only after the replacement works and the user approves removing the old copy.

uBlock Origin filter-list refreshes are managed in the extension's dashboard. They are independent of the CRX version and its update workflow.
