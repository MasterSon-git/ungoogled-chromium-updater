# Security

The updater trusts the specific official GitHub repositories for ungoogled-chromium Windows releases, uBlock Origin, and Chromium Web Store. It queries Google Chrome Version History for the upstream Windows stable comparison and Google's Chrome Web Store update endpoint for locally approved extension IDs. Network requests use standard Windows/.NET TLS certificate validation, pinned host and initial artifact paths, explicit redirect hosts, byte limits and deadlines. Logs are local.

## Updater self-update

The updater uses the fixed `MasterSon-git/ungoogled-chromium-updater` release repository and two exact asset names. The client uses anonymous HTTPS and enforces release identity, immutable release status, a matching SemVer tag and prerelease flag, asset state, byte counts and published SHA-256 hashes. Before opening the ZIP, it verifies a detached RSA signature with the SubjectPublicKeyInfo pin shipped in the active updater. The signature covers a format identifier, repository, tag, byte count and package SHA-256. A bounded manifest must match the archive entries and include the v1 core files. Extraction restricts flat names and file types and rejects reserved names, case-colliding entries, links and oversized content. A bounded worker probe loads the scripts and compiles the CRX verifier. The updater compiles the validated launcher source using the local Windows .NET Framework compiler before activation.

The pinned RSA key provides cryptographic package authentication. GitHub hosts both the packages and the protected environment that holds the signing key. Compromise of the GitHub account, administrators with control over protection settings, an approved signing workflow or an executing dependency may permit malicious signing. A hosting-only attacker can withhold, reorder or replay valid releases. Strictly increasing installed versions limit rollback and still permit a valid intermediate release above the installed version. Signature verification relies on the trusted bootstrap, local account, operating system and runtime. GitHub checksums and immutable releases add hosting-side integrity. [GitHub immutable releases](https://docs.github.com/en/code-security/concepts/supply-chain-security/immutable-releases)

The worker verifies and stages the replacement under the existing update lock in private local storage. The verified handoff waits for the initiating worker and installed launcher to exit, then reacquires the lock, verifies the planned version transition, and switches the app directory and its bundled slot selector. The previous app and worker are retained. An ordinary replacement error restores the app if it has already been moved. A hard interruption between the directory renames may require a verified manual reinstall. Pending browser recovery blocks browser launch on both the normal and resumed paths.

Store the private signing key as an Environment Secret available only after approval of the tag-only `release-signing` job. Build and test run with read-only permissions before approval. Signing checks the unsigned artifact hash and has no publication permission. The publication job verifies the hash and public signature again and uses a separate token permission without the key. Establish and review the public pin independently of GitHub before enabling the feed. An authorized rotation bridge can establish a new pin. Use a trusted manual bootstrap channel to recover from a compromised or lost signing key. [Release and key procedures](docs/releases.md)

Setup and the activated worker use documented Windows Shell APIs to create a per-user shortcut for the fixed updater executable. The private ownership record binds the shortcut path and content hash before setup publishes the link. Setup and uninstall check that record before replacing or removing a link. Windows handles taskbar pinning through explicit user actions. Chromium registration, pin storage and artwork stay under their existing owners. [Shortcut maintenance](docs/maintenance.md#start-menu-shortcut-and-taskbar-pin)

## Browser and extension updates

The example standing policy accepts unsigned Windows installers from the pinned official distribution. Both Automatic and Manual modes pin the release repository and initial asset URL, require the advertised byte count and SHA-256, and check the Windows executable version, architecture, and Authenticode status. GitHub-hosted hashes verify that the downloaded bytes match the hosted metadata. They cannot independently authenticate an unsigned publisher or protect against a compromised distribution account or build pipeline. A signed installer requires valid Authenticode and a configured certificate SHA-256 pin. An unsigned installer cannot satisfy a configured signer pin. Manual approval adds an exact tag and SHA-256 decision without changing these verification rules.

Extension publisher identity is anchored to the signed CRX developer key and exact extension ID. Store packages additionally require the Chromium-pinned Google production proof. A verified package also needs the approved manifest update URL, matching version, published SHA-256 and byte count. Staging writes the exact CRX atomically under private storage and rechecks the digest of cached copies. The console identifies the profile and file, while the persistent log omits both. A download remains pending until Chromium's registration shows the expected ID and version and the checked manifest fields agree with the signed artifact. The updater corroborates those fields against the installed manifest file when the registration provides its standard relative path.

Permission analysis keeps required and optional API and host permissions distinct. It compares each content-script rule as a unit, including its files and filters, and flags changes or removal of selected manifest restrictions. The analysis is conservative and covers a subset of manifest fields. Dynamically registered scripts, code and runtime grants are outside its evidence. Chromium remains authoritative for extension integrity, user grants and permission decisions. [Extension maintenance](docs/extensions.md)

Configuration, state, downloads, logs, backups and installed code inherit a local access control list restricted to the Windows user and SYSTEM. A process running as that user can change these files. Keep the runtime on a local filesystem. The updater avoids following reparse points in profiles, backups and managed storage. Logs contain versions, extension and component IDs, scoped verification counts and operational messages. Backup file paths and their hashes stay in the private completion records. Profile names and browser arguments stay out of the logs.

Before installation, Robocopy compares the full Application and User Data trees by metadata. SHA-256 checks cover all Application files and the documented recovery subset of User Data. Both copies of the scoped content must agree with the closed source's pre-copy hash record. These local checks rely on the integrity of the account, filesystem and private completion record. Keep backups private and use the same Windows account when restoring browser and extension data. The updater checks for the browser before and during copying and verification. Direct launches remain outside the update lock. [Backup scope and recovery](docs/maintenance.md#backup-verification)

Supported signed extension installation and permission prompts stay inside Chromium. The updater uses ordinary local-file command-line arguments, with one invocation per profile. It checks the configured executable, responsive Windows browser instance for the target user-data directory, and MIME handling configuration before forwarding files. It rereads the registration and rehashes each staged file before forwarding. Windows instance discovery is read-only. Chromium remains responsible for integrity and permission prompts, and flags, extension state and installation policies stay under their existing owners. The updater records packages waiting for the Chromium setting separately from requests already passed to Chromium. An early retry rechecks package and profile eligibility. A process creation failure restores the previous submission state. Previously submitted requests require an explicit retry, and installation status requires a later observed matching version and manifest. [Ungoogled Chromium extension FAQ](https://github.com/ungoogled-software/ungoogled-chromium-wiki/blob/master/faq.md) [Chromium Windows instance routing](https://chromium.googlesource.com/chromium/src/+/refs/tags/158.0.8127.88/chrome/browser/process_singleton_win.cc)

Ungoogled Chromium disables the native extension manifest fetch queue. Chromium Web Store schedules checks and initiates downloads on user action. Enterprise force-install implicitly grants permissions and constrains disable and uninstall actions. [Ungoogled Chromium patch](https://github.com/ungoogled-software/ungoogled-chromium/blob/f45ef24307dce0fb5a53e4db4d7e35cdf159745f/patches/core/ungoogled-chromium/disable-webstore-urls.patch) [Chromium Web Store](https://github.com/NeverDecaf/chromium-web-store/tree/v1.5.5.4) [Chromium policy](https://chromium.googlesource.com/chromium/src/+/HEAD/components/policy/resources/templates/policy_definitions/Extensions/ExtensionInstallForcelist.yaml)

The updater extracts the verified installer's payload with the official 7-Zip executable under Program Files. Maintaining a current, trusted 7-Zip installation is a security requirement. The updater reports its version during extraction and the operator is responsible for keeping it current. Extraction requires the known full payload layout and applies archive size, entry and path limits. The installer itself never runs during the test. The latest stable signed full uBlock Origin CRX is verified against the pinned developer identity and official channel before its contents are loaded unpacked in a disposable profile.

The test keeps Chromium's sandbox enabled, directs test traffic to loopback, and uses local DevTools to probe and close the browser instance it started. Extraction and runtime have deadlines. A failed cleanup retains one workspace for manual attention. Only a successful result for the exact verified installer and CRX identities and test version is reused. After installation, matching the tested combination requires the verified browser fingerprint and per-profile evidence for the tested extension. The gate covers unpacked request filtering in isolation. Runtime validation of signed installation, permission changes and other MV2 extensions is separate.

The updater delegates install and repair to the Chromium installer and records a verified distribution revision after installation. During legacy migration it can also record the currently published revision when the existing approval, successful install log, Windows registration, and exact installed payload hashes agree. The migration check reads the installed files and never starts the installer. An unknown installed revision blocks same-Chromium-version installation. The install lock coordinates launchers using this project. Direct launches and other installers remain external to the lock. Chrome Version History is an independent comparison and reports a patch-gap advisory. Consider differences in source and backports when judging CVE applicability. [Chrome Version History](https://developer.chrome.com/docs/web-platform/versionhistory/guide)
